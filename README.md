## Features

- Genre and tag criteria trees, with bulk tree import and export
- Playlists automatically derived from genre/tag criteria, plus manually curated playlists
- Artist, album, and song catalog (every MusicBrainz song, with or without a genre or YouTube video), with play tracking
- Every MusicBrainz song, including songs with no video or no genre, loaded by a staged bulk import (gzip NDJSON parts, Postgres `COPY`, set-based merge); the library list shows only songs with both a video and a genre
- Public reads of one canonical reference dataset (rows with no owner); writes via Google sign-in (admin) or the pipeline API key
- `/health/` endpoint for uptime and database checks
- OpenAPI 3 contract at `GET /schema/`, committed as `openapi.yaml` (generated by `drf-spectacular`)

## Requirements

- Python 3.14
- [uv](https://docs.astral.sh/uv/)
- Docker + Docker Compose (for Postgres, or to run the full stack containerized)

## Setup

### Docker Compose (recommended)

```bash
docker compose up
```

Starts Postgres (`db`) and the API (`api`) with dev-friendly defaults already set in `docker-compose.yml` — no env file needed. The API is served on `http://localhost:8001` (via `manage.py runserver` with the repo mounted for live reload) and exposes a health check at `GET /health/`.

On an empty DB, `api` seeds it in the background with the pinned prod Gold snapshot in `perf/fixtures/` (`scripts/seed_dev_db.py`: genre trees, the converted reference graph, then about 9k songs and their assignments, through the same import endpoints as the nightly sync; see `docs/semantic-cutover-execution.md`), so the genre tree works out of the box. It lacks admin curation: restore prod data (below) when you need it. To reseed: `docker compose down -v && docker compose up`.

### Local (uv + external Postgres)

```bash
uv sync
```

Set the required environment variables (see below), then:

```bash
uv run manage.py migrate
uv run manage.py runserver
```

### Prod data locally

```bash
RCLONE_CONFIG=~/.config/rclone/gtmt-backup.conf R2_BACKUP_BUCKET_NAME=btmt-backups ./scripts/restore-prod-db.sh
```

**Legacy archives:** this script erases the local schema before restoring. Use the [legacy recovery procedure](docs/operations/backup-recovery.md) for backups made before migration 0101.

Replaces the Docker Compose `db` with the latest prod backup (Coolify's daily `pg_dump` to Cloudflare R2), then restarts `api`/`worker`, which apply the current branch's migrations. Includes admin curation that the pipeline Gold exports in `perf/fixtures/` lack. The dump holds only the public canonical dataset, so it is safe on a laptop. Requires [rclone](https://rclone.org/) and a config with an `[r2]` remote (`type = s3`, `provider = Cloudflare`, `endpoint = https://<account-id>.r2.cloudflarestorage.com`) using a **read-only** R2 token scoped to the backup bucket, not the VPS's read/write one. Token setup: infrastructure's [`docs/guides/cloudflare-r2-backup-setup.md` § 5](https://github.com/BehindTheMusicTree/infrastructure/blob/main/docs/guides/cloudflare-r2-backup-setup.md#5-local-dev-read-only-token-prod-db-restore).

To time a migration on prod-sized data without touching the local DB, see [Migration rehearsal](docs/operations/migration-rehearsal.md).

## Environment variables

`WORKLOAD_COORDINATOR_SOCKET` optionally enables the Linux host production-admission protocol. Leave it empty until infrastructure provisions the root-owned coordinator and mounts its socket directory into both API and worker containers. When configured, an unavailable coordinator prevents mutations and task execution. The middleware gates HTTP mutations before their handler; every django-q worker task independently acquires a lease, and direct merges/search rebuilds use the same guard. Successful synchronous work completes its lease. Exceptions, failed worker tasks, server errors and deferred streaming mutation responses leave durable uncertain receipts for operator reconciliation; they cannot authorize a benchmark. Queue admission is serialized at enqueue time: deploy the wrapper to all producers, drain tasks enqueued by older versions and restart workers before enabling benchmarks. Admission/completion failures are recorded as failed django-q results; Redis does not automatically retry them, so operators must reconcile and retry explicitly. Ordinary GET/HEAD/OPTIONS reads do not acquire leases. This does not gate host ETL, backups or other services: their executors must participate before infrastructure enables benchmarks.

## API

Reads (`GET`) on `/v1/*` and `/health/` are public. Writes (`POST`/`PUT`/`PATCH`/`DELETE`) require an `Authorization: Bearer <Google ID token>` for the `ADMIN_GOOGLE_SUB` account. The `X-API-Key` header (set to `PIPELINE_API_KEY`) is for the nightly pipeline and can only write to `genres/tree/import/`, `genres/trees/import-runs/`, `genres/graph/` (`PUT`, deprecated), `genres/graph/import-runs/` and `genres/graph/import/<taskId>/status/`, `library/songs/songs/import-runs/` and `artists/import-runs/` and `regions/map/import-runs/` (create, part upload, commit), `pipeline/imports/unresolved-genre-tags/`, `genealogy/import/`, `curation/wikidata-resolutions/`, `curation/wikidata-items/`, `pipeline/runs/` (`full` only), `pipeline/runs/claim/` and `pipeline/runs/{uuid}/`, and read `curation/export/` and `pipeline/runs/latest/`; other writes with it return 403 `permission_denied`. The `X-API-Key` header set to `CURATION_API_KEY` is the `curator` role for agents: it can only read and write `curation/<list>/entries/` and `curation/edges/` (history attributes its writes to the `curation-bot` user), and `curation/export/` stays pipeline/admin-only. No credentials returns 401 `authentication_required`, an invalid or expired token 401 `invalid_token`, and a verified non-admin Google account 403 `permission_denied`. `GET /v1/auth/me/` returns the caller's `{"role", "email"}` (401 when anonymous). Reference data has no owner (`user IS NULL`) and is the same for every caller; a Google sign-in creates a `User` keyed by the account's `sub`, which owns nothing yet.

### Genre alias targets

`genre_alias` rows use `musicbrainz_genre_name`, `target_item_id` (Wikidata QID or `LOCAL:` id), `wikidata_genre_name` (last label recorded when selecting a target) and `reason`. To select a target, an admin or curator queries `GET /v1/curation/genre-alias-targets/?q=`; it returns `{publishedOn, curationExportedOn, results: [{id, label, tree}]}` from the most recently published Gold match catalogue. The endpoint returns 503 before the first publication. An older client writing a label must supply an exact label with a single eligible result.

`GET /v1/curation/export/` always carries the `target_item_id` column of the genre aliases. After the trees and graph are imported, `POST /v1/pipeline/imports/unresolved-genre-tags/` accepts the Gold file with optional `genreAliasReview`. Its `curationExportedOn` must match the applied export. A replay of the same report returns 200. The API only queues issues for aliases whose saved revision matches the export. `GET /v1/curation/review/` includes these issues alongside the other review items.

Run responses include nullable `stepTelemetry`. For a full run, the launcher may send it in a heartbeat or terminal PATCH. The first update supplies a `variant` (`bronze_only`, `legacy_silver` or `split_silver`). Each supplied `foreground` or `wikidata` array replaces that chain with its current snapshot. Entries hold `stage`, `startedAt`, `finishedAt` (null while running) and `state` (`running`, `succeeded`, `failed` or `cancelled`). A supplied `wikidataRetry` describes the last WDQS retry with `attempt`, `reason` and nullable `httpStatus`. Send null to clear it. Omitted telemetry keys retain their last value.

An admin edit of a wikidata-backed genre also upserts the curation rule that makes the pipeline reproduce it, with reason `grow admin edit by <pseudo>`: a rename goes to `label_overrides`, a global reparent to a `classification` `assert` edge (the replaced curated parent's edge is deleted and the parents the reference graph gives it are prohibited), a root acceptance to the `global_roots` list, and an exclusion to `<category>_genres`. Edits no list expresses return 400: a reparent to a root, under an app-created genre, or in the regional tree (grow can't tell whether the new parent is a regional overview or a regional genre). Genres without a `wikidataId` are app-created, absent from the pipeline's output, so their edits only lock the row.

Full request/response details per resource are documented in [`docs/api/`](docs/api/).

### Retiring `expression_styles`

Deploy the compatible curation Bronze reader ([Pipelines #461](https://github.com/BehindTheMusicTree/the-music-tree-pipelines/pull/461)) before deploying Grow migration `0155`. Pause curation edits for the migration window. Move any remaining `expression_styles` entries to genre classification edges before migrating. Migration `0155` aborts while the list contains entries.

If a legacy style uses a `LOCAL:` identity declared only in `local_identities`, resolve or materialize that endpoint through the genre addition workflow before creating its replacement edge.

Back up the curation data before upgrading so you can recover the original `local_identities.kind` values and review reports if needed. The migration changes `expression` identities to `genre` in place and clears review items for the retired list. Reversing the migration restores the previous list choices only. The curation export omits `expression_styles` after deployment. The history endpoint still accepts `?list=expression_styles`.

Before rolling back to the previous Grow version, remove or restore any regional membership prohibitions added since the upgrade that target a declared local genre. The previous version rejects these rules when exporting curation.

A [Bruno](https://www.usebruno.com/) collection for manual testing is at [`bruno/Track/`](bruno/Track/) — open it in the Bruno app, select the `local` environment, and set the `API_KEY` secret to your `PIPELINE_API_KEY`.

## Operations: resetting the catalogue

`manage.py reset_catalogue --confirm <database name>` empties the catalogue (songs, artists, genres, playlists, graph, import state) in a single `TRUNCATE`, so the next pipeline run imports into an empty base. Curation (entries, edge rules, exports), users, pipeline run history and the curation history are kept. The tree import recreates the Genreless and Tagless playlists.

- `--confirm <db>` is required and must match the database name.
- `--dry-run` lists the tables and estimated row counts, then exits.
- `--include-user-data` is required when user-owned tracks, playlists or plays exist; without it the command refuses.
- It refuses while an import or a pipeline run is active (wait for `wait_for_import_drain`).
- Back up the kept tables first, then run the genre tree import before the songs and artists imports.

## Performance

Three gates keep endpoints fast. The query budgets run in `Pytest`, and `Perf` runs the latency SLOs and the A/B gate. Both are required checks on `develop` and `main`. `Perf` is a gate job over `Perf route` and `Perf run` (the heavy job); `Perf route` and `Perf run` are not required themselves. A failed `Perf route` fails `Perf`. Changing a budget or an SLO is a deliberate, reviewed diff, not a way to make CI pass.

- **Query budgets** (`tests/integration/perf/test_query_budgets.py`, part of `uv run pytest`): each endpoint must run a fixed number of queries whatever the number of rows, and exactly its `BUDGETS` data-statement entry. Transaction commands have a separate exact protocol: one snapshot boundary, PostgreSQL read-only `REPEATABLE READ` before data reads, and no redundant savepoints. Unrecognized SQL counts as data work; totals include both categories. These checks run outside test-managed transactions. A gain lowers the data budget in the same PR.
- **Latency SLOs** (`perf/`, CI job `Perf`): median latency per endpoint on Postgres (p95 is printed too), seeded with a pinned snapshot of the prod pipeline's Gold exports (`perf/fixtures/`), imported through the same endpoints and in the same order as the nightly sync.
- **A/B regression gate** (CI job `Perf run` on PRs, `scripts/perf_ab.sh`): the PR's base and head run `perf/` in turn on the same runner (base, head, base, head), each on its own seeded database. Before every measured round, `VACUUM (FREEZE, ANALYZE)` resets visibility and planner statistics: rolled-back reparenting still grows physical tables and can otherwise trigger JIT compilation only in later rounds. `perf/compare.py` pairs round i of base with round i of head (back to back, so runner drift cancels) and fails a scenario whose median head/base ratio exceeds `RATIO` **and** adds more than `FLOOR_MS`, or that runs more data queries. Captured requests assert the exact transaction protocol separately, using the same accounting as the fixed query budgets; the full transaction remains inside the latency measurement. Every measured run is checked and the worst data-query count is compared. Older base results without explicit transaction statements already report data-query counts. A suspected regression gets two more rounds before the verdict. A side whose rounds split into two groups that far apart is `unstable` and fails too: its pooled median would sit between two query plans. With four rounds or more, each group needs at least two rounds, so one odd round is noise, not a split. The runner's drift is estimated per round within the side and removed first, so a slowdown shared by every scenario is not flagged; the summary shows each round's p50 and the drift. This catches what an absolute SLO can't: a 13 ms endpoint going to 130 ms under a 150 ms SLO. The table lands in the job summary. An SLO breach the base shares (`over SLO (base too)`) is reported, not failed on a PR: the A/B judges the PR, the SLO judges `develop`. Pushes to `main` and `develop` judge the SLOs only; `workflow_dispatch` compares a ref with itself to measure noise, so every breach there is shared and reported, not failed.
- **Routing** (`scripts/perf_route.py`, job `Perf route`): a PR whose changed files (both names of renames included) are all on an explicit non-runtime allowlist (docs, `*.md`, agent config, unrelated workflows) skips `Perf run`, and the `Perf` gate passes. Unknown paths, mixed diffs, an empty or unavailable diff, pushes and `workflow_dispatch` run in full. A failed `route` fails the `Perf` gate.
- **Accepting a regression** (a deliberate trade-off, for example a feature that must do more work): add the `perf-regression-accepted` label to the PR, which reruns `Perf` with slowdowns and query increases reported but not failed. SLOs still apply.

The absolute SLOs use 3× the slowest side's pooled median across five CI self-comparisons on 2026-11-07, rounded up to 10 ms (100 ms when the ceiling is at least 1 s). For example, artist genre counts measured about 9 ms (30 ms SLO), the largest genre's track page about 84 ms (260 ms), and the 100-row genre playlist list about 155 ms (470 ms). This covers runner-speed variation while the A/B gate still catches relative regressions. Calibration runs: [1](https://github.com/BehindTheMusicTree/grow-the-music-tree-api/actions/runs/42382519148), [2](https://github.com/BehindTheMusicTree/grow-the-music-tree-api/actions/runs/42382845469), [3](https://github.com/BehindTheMusicTree/grow-the-music-tree-api/actions/runs/42383175534), [4](https://github.com/BehindTheMusicTree/grow-the-music-tree-api/actions/runs/42383477978), [5](https://github.com/BehindTheMusicTree/grow-the-music-tree-api/actions/runs/42383729328). ### Genre selection and counts

Genre-playlist track reads accept `coverage=genre_only|genre_and_subgenres`.
Inclusive playlist reads accept `subgenres=global|regional|all`: global genres default to `global`,
regional genres default to and require `all`. Exact coverage rejects `subgenres`; Genreless rejects both parameters.
Primary paths are deduplicated; secondary parents do not contribute. Global coverage never crosses a regional
node on its way to another global genre. Regional coverage includes the selected genre and reachable regional
genres; `all` combines those selections. A regional root's `all` includes all its primary descendants.
Playlist track reads and summary counts still use the display-tree projection and stored playlist memberships.
The [song catalogue filter](docs/api/songs.md#list-by-genre) uses the semantic reference graph and accepts contract 4 scopes.

Genre playlist summaries expose `genreOnlyTracksCount` and `genreAndSubgenresTracksCount` (`global`, `regional`,
`all` for global genres; only `all` for regional and Genreless). These count actual members of that playlist,
not the sum of other playlists' members. `catalogue` contains the same shape for all catalogue songs, including
songs without playable video. Legacy `tracksCount` follows the default membership selection; tree `songsCount`
follows the default catalogue selection. Genre detail's legacy `tracksCount` remains a catalogue count.
Artist-filtered trees have the same population separation and are not stored in the global tree cache.

Playback applies the selection before anchors, ordering and pagination. Its queue additionally respects country
availability; a global membership count does not guarantee playback in the viewer's country. Country does not
change the global summary or its cache key.

`uv run python manage.py verify_genre_membership_counts` independently checks the stored membership buckets.
`--repair` explicitly rebuilds them atomically and invalidates the tree cache. PostgreSQL source writes and repair
require the default READ COMMITTED isolation and share a transaction advisory lock; the existing tree-version row
also serializes tracked writers. Long import transactions therefore block other source writers until commit.
Reads remain unlocked. List/detail summaries use one statement for catalogue, graph and selected membership
inputs, and an uncached tree adds one query; playback remains four queries. This tradeoff avoids
one membership scan per genre or folding child playlists whose actual members may differ. The latest catalogue
graph and catalogue inputs are reused within a worker when the statement observes the same tree version;
actual playlist membership is always read again. Rolled-back writes cannot leave stale summary values.

`uv run python manage.py verify_genre_catalogue_counts` compares canonical Song/Track joins with the
sparse catalogue buckets. It includes unplayable and
genreless songs, reports drift without changing data, and exits unsuccessfully on a mismatch. An absent
catalogue bucket means zero. Missing required genre playlists or the tree-version singleton are configuration
errors rather than zero counts.

Use `--repair` explicitly to rebuild the projection in one transaction, retaining the original mismatch
report and independently checking the result before commit. Repair removes orphan catalogue buckets but
does not create or remove playlists. `--database <alias>` selects the database. On PostgreSQL, verification
and repair require READ COMMITTED isolation and acquire the same source-write gate as membership repair;
ordinary detail requests do not acquire that gate.

Migration `0115` installs catalogue maintenance on both halves of the Song/Track join and backfills while
source writers are excluded. Relation locks precede the advisory gate. A busy source relation or gate makes
the migration fail immediately and roll back; retry after the writer completes. This migration temporarily
takes exclusive source-table locks; its operational window must be measured on representative data.


### Semantic reference graph (draft)

Semantic song-assignment staging is available as a preview with reviewed revisions and durable part receipts; commit remains disabled pending the catalogue, playlist and search cutover. See the [song import contract](docs/api/songs.md#import). Legacy imports remain blocked once a reference graph is active.

`GET /v1/genres/graph/` returns the graph, semantic identity-to-genre UUID
mapping, graph `revision` and `membershipRevision`. To get only the expected
revision for a graph write, use the public `GET /v1/genres/graph/revision/`. It
returns HTTP 200 with `{"revision": "<uuid>"}`, or `{"revision": null}` before
the first publication, and sets `Cache-Control: no-store`. Reviewed song imports
still use both revisions returned by the graph write or its task result.

Pipeline/admin `PUT` accepts
`graph`, a complete `mapping` (existing genre UUID or `null`),
and `expectedRevision` (`null` for the initial import). The graph must carry the
current curation export timestamp. A `null` identity keeps its existing
binding; otherwise it adopts the ownerless genre whose `wikidata_id` equals the
identity (the Gold id), or gets a new genre when there is none. Ambiguous
`wikidata_id`s and genres already bound to another identity answer 400. Missing
mappings and stale revisions fail. Curator/admin `POST /v1/genres/graph/restore/` accepts the archived `revision` and
the current `expectedRevision`.

`POST /v1/genres/graph/import-runs/` takes the same body as `PUT` and returns 202 `{taskId}`; the import runs as an async
import run (it avoids the `query_timeout` 503 of the synchronous `PUT` at prod scale). Poll
`GET /v1/genres/graph/import/<taskId>/status/`. `PUT /v1/genres/graph/` is deprecated and will be removed.

Both operations require `contractVersion: 4`. A classification (restricted or a regional expression) can coexist
with derivation on the same directed pair. An explicit influence on a pair already classified or derived is rejected
with 400 before publication. Derivation and influence alone grant no semantic descendant access.

`GET /v1/library/songs/<song UUID>/attributions/` returns `revision`,
`membershipRevision`, `assignmentRevision`, complete direct `attributions`,
`effectiveAttributions` and `needsRefinement`. Curator/admin `PUT` on the same
route accepts zero or one semantic identity, with an array of independent evidence decisions for that genre:

```json
{
  "expectedRevision": "<graph revision UUID>",
  "expectedMembershipRevision": "<membership revision UUID>",
  "expectedAssignmentRevision": "<assignment revision UUID or null>",
  "attributions": {
    "LOCAL:expression": [
      {"decisionId": "<permanent decision ID>", "source": "<source>", "rationale": "<justification>"}
    ]
  }
}
```

`expectedAssignmentRevision: null` creates the first assignment set; subsequent
edits require the token returned by the latest GET, including after clearing the
set with `attributions: {}`. A stale graph, population or assignment token returns
409; reload all tokens and assignments before resolving the edit. Evidence order
does not change the set. Reusing a decision ID with different content fails;
several independent decisions for the same identity are preserved. A successful
PUT returns all three current tokens. A song has at most one directly assigned
genre; it inherits all semantic parents through deduplicated graph paths. Writes
and restores containing several direct genres are rejected. Graph-only songs
are included in song lists. Song cursors now contain a UUID alone; previous
cursors must be restarted. Graph import is required before listing songs.
Song-list name and umbrella filters use normalized graph attributions. Each list
holds a consistent graph through counts, pagination and serialization, returning
`X-Genre-Graph-Revision` and `X-Genre-Membership-Revision` response headers.
Genre/playlist list, detail and tree responses also evaluate their data within
one read-only REPEATABLE READ snapshot after authentication. Readers can overlap
publication; response bodies and cache validators describe the same committed
state. Lazy querysets must be evaluated before leaving the snapshot.

Graph/membership archives and initial assignment backups are retained. Imports
and graph restores require `retirements` for every removed identity, each with
`{"target": "<retained identity>"}` (or an explicit `null` to unassign) and
`provenance: {decisionId, source, rationale}`. Complete direct assignments are
archived before any remap. Retired genre UUIDs and semantic identities remain
reserved; reintroducing an identity reuses its original UUID, including when
several concepts share a display label.

Graph publication updates stored song genres in the same transaction as the
graph. The first publication reconciles the full catalogue. Subsequent imports,
merges and restores reconcile only songs affected by changed assignments or
bindings. A graph restore reuses the archived UUID bindings for identities in
that revision. It preserves the assignments already moved by a merge unless a
new retirement remaps them.

The genre-kit migration 0023 clears the old access index. Before deploying over an active graph, retain the payload,
revision and UUID mapping and prepare a compatible contract 4 import with explicit retirements for removed identities.
Keep graph-dependent traffic gated until the import has rebuilt the access index. A pre-v4 archive is retained for
recovery with its compatible runtime and database backup. To use its contents on the new runtime, validate a converted
contract 4 payload and publish it as a new import. Reverting the migration alone leaves the old access index empty.

Curator/admin `POST /v1/genres/graph/assignments/restore/` accepts the initial
import `revision`, `expectedRevision`, `expectedMembershipRevision` and explicit
`provenance`. It restores surviving songs' initial assignments through the
archived genre UUIDs' semantic bindings; required identities must be active.
It snapshots current assignments first and preserves songs added after cutover.
An identical retry with current revision tokens makes no changes.

Catalogue/playlist counts, search,
legacy writes and bulk imports still require migration to semantic memberships.
Do not mix the old write APIs with graph attribution writes.
